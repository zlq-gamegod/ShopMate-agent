# Bad Case 记录（S6）

> 记录格式：现象 → 定位 → 原因 → 修复 → 效果
> 数据来源：45 条调优集 `eval/eval_set.jsonl` + 20 条留出集 `eval/eval_set_holdout.jsonl`
> 评测配置：`MODEL_TEMPERATURE=0`，`--repeat 3`（同一条跑 3 次，2 次通过才算通过）

## 评测口径先说清

四个指标的定义（`eval/eval_e2e.py`）：

| 指标 | 算法 | 健康量级 |
| --- | --- | --- |
| 通过率 | 期望工具全部调到 且 key_points 全部出现 | ≥0.85 |
| 检索执行率 | policy / multi_hop 样本中 `route == expect_route` 的比例 | 接近 1.0 |
| 含未溯源数字率 | 答案中的业务数字（≤4 位）在证据里找不到的样本占比 | ≤0.1 |
| 平均轮次 | 每条样本 AIMessage 数量均值 | 2–3 |

两点必须交代，否则数字不可信：

1. **为什么加 `--repeat 3`**：qwen-plus 即使 `temperature=0` 也不完全确定，同一份代码重跑，通过率会在 ±2 条（±4.4pp）范围抖动。单次跑的噪声比大多数优化的收益还大，不加多数投票就无法归因。
2. **为什么有留出集**：45 条调优集是「边看失败边改」改出来的，属于训练集成绩。留出集 20 条只跑一次、不做任何针对性修改，那个数字才代表泛化能力。

版本轨迹（前 5 版单次跑、temp=0.7；后 3 版 temp=0、3 次多数）：

| 版本 | 改动 | 通过率 | 检索执行率 | 未溯源 |
| --- | --- | --- | --- | --- |
| v1 | 基线 | 64.44% | 60.87% | 0% |
| v2 | 补 `lexicon.py` 关键词 | 77.78% | 100% | 0% |
| v3 | 提示词 3 条 → 6 条 | 86.67% | 100% | 0% |
| v4 | 铁律 3 收紧（时效必须报签收天数） | 91.11% | 100% | 0% |
| v5 | 退款试算工具契约（允许按描述推断类型） | 95.56% | 100% | 0% |
| — | 只改温度（0.7 → 0） | 93.33% | 100% | 0% |
| v6 | 铁律 7（状态词原样引用） | 91.11% | 100% | 0% |
| **v8** | 铁律 7 + 8、补「已取消」资金映射 | **97.78%** | **100%** | **0%** |
| — | **留出集 20 条（未调优）** | **95.00%** | 90.91%* | 0% |

\* 留出集原始输出 72.73%，其中 2 条属标注口径不一致（见文末附录 A），按调优集口径重算为 90.91%。

## Case 1：路由漏判，检索根本没发生（H03，留出集）

**现象**

问：「东西有点小瑕疵但我想留着用，跟卖家协商部分退款的话，平台一般按什么比例裁定？」

答：

> 平台不按固定比例裁定协商部分退款，具体金额由买卖双方自行协商达成一致。如协商不成，可申请客服介入处理。

3 次跑全部失败（0/3）。规则文档 `02_refund_policy / 部分退款与协商折价` 明确写着：协商不成的转客服介入按责任比例裁定，**常见的裁定比例是 10%–30%**。模型答的「不按固定比例」是凭空编的。

**定位**

先看路由，再看检索：

```
classify("...部分退款...比例裁定")  →  other
命中的 POLICY 关键词：[]          ← 一个都没中
```

再单独验检索能力：

```
hybrid_retriever("部分退款 协商折价 瑕疵 裁定比例")
[0] 部分退款与协商折价 … 常见的裁定比例是 10%–30%   ← 排名第一
```

两条结果对照说明：**检索能力足够，是路由没有触发检索**。问题被卡在 `nodes.py` 的分支上——`route == "other"` 直接进 `agent_node`，`retrieved` 为空，模型手里没有任何条款，只能自由作答。

**原因**

`lexicon.py` 的 `POLICY` 词表是照着 45 条调优集补的，覆盖了「自然日」「起算」「划扣」「强制介入」「退多少钱」这些**具体说法**，但没有覆盖「部分退款」「折价」「瑕疵」「比例」这一组同义表达。关键词路由的召回上限 = 词表覆盖度，换个说法就漏。

**修复**

**没有修。** 这是刻意保留的。

留出集的作用就是量出「调优集上看不到的天花板」。为了让 H03 通过而回改 `lexicon.py`，等于把留出集并入训练集，95% 这个数字会立刻失去意义。正确做法是把它作为证据记下来，指向结论：

> 规则的触发不该靠关键词穷举。同义表达是开放集合，补词永远补不完；到这一步应当换成小模型/语义分类（把 `classify` 从词表匹配换成一次 few-shot 分类调用，或直接用 embedding 相似度匹配若干条「问法示例」）。

**效果**

留出集 19/20 = 95.00%。这一条是**唯一失败样本**，也是「关键词路由已饱和」的直接证据——调优集 100% 的检索执行率是词表拟合的结果，不是能力。

## Case 2：检索到了条款，模型只答了否定（E009，调优集）

**现象**

问：「确认收货超过 20 天了，还能申请平台强制介入吗？」

答（temp=0，单次）：

> 不能。确认收货超过 15 个自然日，售后入口关闭，平台不再受理强制介入。

结论正确，但**只答了「不能」**。同一段规则的后半句是「只能与卖家协商，或走司法途径」——用户真正需要的是这条退路。v6 那一版同样是 FAIL。

**定位**

第一反应是检索没召回，打算把 `top_k` 从 5 提到 6。先查了一下：

```
召回第 [0] 块（排名第一）：
"超过 15 日：售后入口关闭，平台不再受理强制介入，只能与卖家协商，或走司法途径。"
```

**「协商」那段条款本来就在排名第一的块里。** 提高 `top_k` 只会多塞 4 块无关内容，成本和噪声都上升。`top_k` 一个字没动。

那就只剩一种解释：上下文给到了，是模型在生成时把「给用户一条出路」这一步丢了——典型的「答结论不答方案」。

**原因**

提示词里的铁律只管「不许编造」「先查工具」，没有任何一条要求**否定性结论必须配替代路径**。模型按「只回答对方问的那一件事」的指令，把问题当成是非题处理。

**修复**

`nodes.py` 的 `SYSTEM_TMPL` 加铁律 8：

```
8. 结论是「不能 / 不支持 / 超期」时，必须同时给出规则允许的替代路径
   （与卖家协商、申请客服介入、举报违规、走司法途径等），不能只回一句否定。
```

**效果**

| | E009 | E010（同类：超期假货） | policy 分类通过率 |
| --- | --- | --- | --- |
| v6（temp=0） | FAIL | FAIL | 10/12 |
| v8（加铁律 8 后） | **3/3 PASS** | **3/3 PASS** | **12/12** |

同类样本一次修好两条，说明失败模式是**通用的**（「否定不给出路」），不是单条题目的偶然。

## Case 3：工具映射缺一个键，模型被迫转人工（E022，调优集）

**现象**

问：「ORD202610200004 订单已经取消了，钱退回到我这里了吗？」

答（v6，temp=0）：

> 钱未在担保中，状态为「未知」，需人工核实。

v7 三条跑只过 1 条（1/3），且 `query_guarantee` **确实被调用了**——工具调了、答案还是错，说明问题在工具返回值，不在模型。

**定位**

直接调工具看返回：

```
query_guarantee("ORD202610200004")
→ {"status": "未知", "release_condition": "该状态无对应规则，需人工核实。"}
```

再看订单状态：`已取消`。

再看映射表 `agent/tools.py`：

```python
_GUARANTEE_BY_STATUS = {
    "待付款": ("未支付", ...),
    "待发货": ("担保中", ...),
    "已发货": ("担保中", ...),
    "已签收": ("担保中", ...),
    "退款中": ("冻结中", ...),
    "已完成": ("已放款", ...),
    "已退款": ("已退回", ...),
    "已关闭": ("已退回", ...),   ← 有「已关闭」
}                                ← 没有「已取消」
```

订单状态有 9 种取值，映射表只写了 8 种，**唯独漏了「已取消」**。工具返回「未知」，模型没有任何依据，只能答「需人工核实」——它并没有答错，是数据断了它。

**原因**

状态枚举和映射表分两处维护，没有一致性校验。这类 bug 的共同特征：**工具调用率 100%，通过率照样掉**。只看「工具有没有被调用」的指标（`tool_recall`）完全发现不了，必须对照工具的**返回值内容**。

**修复**

补一行：

```python
"已取消": ("已退回", "订单已取消，货款由平台原路退回买家。"),
```

**效果**

| | E022 | multi_hop 分类 |
| --- | --- | --- |
| v7 | 1/3 FAIL | 10/11 |
| v8 | **3/3 PASS** | 10/11（唯一失败 E019 属标注问题，剔除后 11/11） |

**遗留建议**：加一条启动自检，断言「`orders.json` 里出现的所有订单状态」都能在 `_GUARANTEE_BY_STATUS` 里找到，否则启动即报错。这类缺键 bug 应该在启动时暴露，而不是等评测跑出来。

## 附录 A：E019 是标注错误，不是代码错误

**现象**

问：「ORD202610200005 退款被卖家拒绝了，接下来我该怎么办？」

答（v8，0/3 FAIL）：

> 卖家已拒绝退款，当前处于小法庭投票中……等待评审团投票结束（截止 2026-11-11 23:59:59），结果 2 小时内公布。

`key_points` 我写的是 `["客服介入"]`，答案里没有，判 FAIL。

**定位**

查 `disputes.json`：

```json
"ORD202610200005": {
  "stage": "小法庭投票中",
  "next_step": "等待评审团投票结束，结果在截止后 2 小时内公布"
}
```

这个订单**已经进入小法庭了**，下一步确实是等投票结果，不是申请客服介入。**答案是对的，标准答案是错的。**

**处理**

不改 `key_points`。评测集一旦修改，v1–v8 的对比就全部失效。记为「已知标注错误」，报告里注明：剔除后 45/45。

对外报 97.78% 而不是 100%——报 100% 经不起追问，而 97.78% 加上这条说明，反而显得更可信。

## 附录 B：评测抓不到的真实瑕疵（未修）

E019 那条答案里还有一句：「你已提交 3 票，卖家 1 票」。

`disputes.json` 的字段是 `votes_buyer: 3` / `votes_seller: 1`，实际含义是**大众评审员中投给买家/卖家的票数**，不是买家本人投了 3 票。字段名有歧义，模型按字面理解，于是把「评审员 3:1」说成「你投 3 票、卖家 1 票」。

这类错误**四个指标全都抓不到**：没有漏调工具、key_points 也命中、数字 3 和 1 在证据里查得到（只是语义被曲解）。只能靠人工读样本。

两种修法（任选）：

- 数据侧改名：`votes_for_buyer` / `votes_for_seller`
- 工具侧加说明：`get_dispute_status` 返回里补 `"votes_note": "以上为大众评审员投票数，非买家/卖家本人投票"`

## 三条 case 的共性

| | 卡在哪一层 | 表现 | 修在哪 |
| --- | --- | --- | --- |
| H03 | 路由（关键词覆盖） | 检索从未发生，模型凭空答 | 未修，指向换语义分类 |
| E009 | 生成（提示词约束） | 上下文给到了，答案丢了一半 | 提示词加一条 |
| E022 | 工具（数据映射） | 工具调了，返回「未知」 | 补一个字典键 |

同一个「答错」，可能坏在三个完全不同的地方。**判断顺序应该是：先看路由走没走对 → 再看检索召回没有 → 再看工具返回了什么 → 最后才怀疑模型。** 反过来（先怀疑模型、先去改提示词）会把数据层的 bug 越埋越深——E022 如果一开始就去调提示词，永远修不好。
